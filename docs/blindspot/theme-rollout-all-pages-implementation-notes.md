## 2026-07-27 — 공용 파일 둘 수정 완료. 설계와 달라진 것 셋

- 결정 1: 코드 상자 안 글자색은 팔레트 변수가 아니라 고정값 그대로 옮겼다.
  설계 문서는 "여섯 규칙을 옮긴다"고만 적었다.
  옮기면서 변수로 바꾸고 싶은 유혹이 있었지만 그대로 뒀다.
  코드 상자 배경이 밝은 모드에서도 어두운 채로 남기 때문이다.
  변수로 두면 어두운 글자에 어두운 배경이 된다.
  직전 작업에서 같은 실수로 미달 393건이 나온 적이 있다.

- 결정 2: 밝은 모드 상자 배경에 대비값을 함께 적었다.
  `var(--g-bg-2, #161B30)` 처럼 기본값을 붙였다.
  `--g-bg-2` 는 밝은 모드 색 목록에 일부러 없는 이름이다.
  이름이 없으면 값이 비어 규칙이 통째로 무시된다.
  기본값을 적어 두면 그 경우에도 의도한 색이 나온다.
  설계 문서는 이 안전장치를 적지 않았다.

- 결정 3: hero 제목의 그러데이션 세 색을 새 팔레트로 바꿨다.
  설계 문서의 색 대응표에 이 항목이 없었다.
  기존 값이 본문색과 링크색과 강조색을 섞어 쓰고 있었다.
  개편한 발표자료와 같은 보라·민트·분홍 세 색으로 통일했다.

- 검토한 대안: 셋 다 그대로 두는 방법이 있었다.
  첫째는 두면 밝은 모드에서 코드가 안 보인다.
  둘째는 두면 밝은 모드에서 상자 배경이 사라진다.
  셋째는 두면 hero 제목만 예전 색 조합으로 남는다.
- 보수적 선택 여부: 예. 셋 다 기존 구조를 유지하는 쪽을 골랐다.
- 계획과의 이탈: 있음. 설계 문서에 없던 판단 셋이 추가됐다.
  방향은 설계 문서의 결정 4·5·11과 같다.
- 사용자 확인 필요: 아니오

## 2026-07-27 — 견본을 검사에 넣자 실패 셋. 둘은 검사 자체가 틀렸다

- 실패 1: "시차 등장이 걸린 슬라이드가 하나도 없다".
  검사가 틀렸다. 견본은 장마다 등장 항목이 하나뿐이다.
  항목이 하나면 시차를 잴 대상이 없는데 검사는 그것을 실패로 봤다.
  고침: 항목이 둘 이상인 장이 있을 때만 이 판정을 한다.

- 실패 2: "밝은 모드 화면 6: 선명도 1".
  검사가 틀렸다. 도표 도구가 그림 안에 스타일 정의를 글자로 넣는다.
  그 글자는 화면에 안 그려지는데 검사가 본문으로 셌다.
  고침: 화면에 안 그려지는 종류의 요소를 검사에서 뺀다.

- 실패 3: "화면 4: 세로 838px". 이것만 진짜다.
  사용자가 이번에 고치기로 한 기존 넘침이다.
  고침: 첫 문장을 두 줄에서 한 줄로 줄였다.
  "열전도 계수"를 "계수", "온도 기울기"를 "기울기"로 줄였다.
  수식 기호 둘은 그대로 남겼다. 그 둘이 이 장의 요점이다.
  결과 838에서 764가 되어 36픽셀 여유가 생겼다.

- 검토한 대안: 실패 3은 설명 줄 하나를 통째로 지우는 방법이 있었다.
  견본은 기능을 보여 주는 자료라 줄을 지우면 보여 줄 것이 준다.
- 보수적 선택 여부: 예. 내용을 지우지 않고 말만 줄였다.
- 계획과의 이탈: 있음. 설계 문서는 검사가 틀릴 가능성을 적지 않았다.
  검사를 두 곳 고치는 일이 늘었다.
- 사용자 확인 필요: 아니오

## 2026-07-27 — 회귀 시험 중 git checkout 으로 미커밋 변경을 날림

- 무슨 일: 검사가 결함을 잡는지 시험하려고 공용 파일을 일부러 망가뜨렸다.
  되돌릴 때 `git checkout` 을 썼다.
  그 파일은 아직 커밋한 적이 없어서, 그 명령이 이번 작업의 수정 전부를 지웠다.
  구문 색과 등장 규칙과 기준 글자 크기 등 열 곳 넘는 수정이 한 번에 사라졌다.
- 어떻게 알았나: 되돌린 직후 검사를 다시 돌렸더니 통과할 것이 실패했다.
  밝은 모드 코드 주석 선명도 3.62 가 다시 나왔다.
  그 값은 이번에 고친 항목이라 되살아났다는 것은 수정이 사라졌다는 뜻이다.
- 고침: 지운 수정을 전부 다시 넣었다. 검사로 복구를 확인했다.
- 결정: 앞으로 회귀 시험은 파일 복사본으로만 되돌린다.
  `git checkout` 은 커밋 이전 상태로 돌리므로 이번 작업분까지 지운다.
- 검토한 대안: 시험 전에 먼저 커밋해 두는 방법이 있었다.
  아직 확인이 안 끝난 상태를 커밋으로 남기고 싶지 않았다.
- 보수적 선택 여부: 예. 복사본 방식은 이번 작업분을 건드리지 않는다.
- 계획과의 이탈: 없음. 절차상의 사고이고 결과물은 원래대로다.
- 사용자 확인 필요: 아니오

## 2026-07-27 — 검사를 고치다가 검사 자체를 조용히 죽일 뻔했다

- 무슨 일: 검사 2의 거짓 실패를 고치면서 결과 항목 이름을 바꿨다.
  그런데 그 이름을 쓰는 판정 조건은 안 고쳤다.
  없는 이름을 읽으니 조건이 항상 거짓이 되어 판정 블록이 통째로 건너뛰어졌다.
  검사는 아무 일도 안 하면서 통과만 하는 상태가 됐다.
- 어떻게 알았나: 고친 검사가 결함을 잡는지 다시 시험했다.
  일부러 등장 지연을 죽였는데 검사가 통과했다.
  통과할 리가 없는데 통과해서 검사를 뜯어봤다.
- 고침: 판정 조건이 읽는 이름을 결과에 다시 넣었다.
  고친 뒤 같은 시험에서 항목 28개를 잡아냈다.
- 배운 것: 검사를 고친 뒤에는 반드시 결함을 다시 심어 봐야 한다.
  "통과"는 검사가 제대로 도는지에 대해 아무것도 알려 주지 않는다.
  이것은 이 저장소가 화면 렌더링 검사를 만든 이유와 정확히 같은 실패 방식이다.
- 검토한 대안: 없음. 검사를 고쳤으면 다시 시험하는 것이 유일한 답이다.

## 2026-07-27 — 옮기는 과정에서 규칙 둘을 빠뜨린 것을 발견

- 무슨 일: 덱의 인라인 규칙을 공용으로 옮길 때 색 규칙 둘이 사라졌다.
  첫째, 굵은 글자의 호박색이다. 옮긴 곳이 없어 그냥 없어졌다.
  둘째, 소제목 색이다. 덱은 민트로 덮어 썼는데 그 덮어쓰기가 사라져 보라로 돌아갔다.
- 어떻게 알았나: 새로 만든 호박색 이름이 선언만 되고 쓰이는 곳이 0인 것이 이상했다.
  덱에서 지워진 줄과 공용 파일에 있는 줄을 맞대 보니 둘이 안 맞았다.
- 왜 검사가 못 잡았나: 둘 다 색이 바뀌었을 뿐 대비비는 기준을 넘는다.
  검사는 "읽히는가"만 보고 "의도한 색인가"는 안 본다.
  화면 렌더링 검사도 이 종류는 원리적으로 못 잡는다.
- 고침: 두 규칙을 공용 파일에 넣었다.
  강조 세 자리가 서로 다른 색을 쓰는 이유도 주석으로 적었다.
  소제목은 민트, 표 머리는 보라, 굵은 글자는 호박이다.
- 검토한 대안: 소제목을 보라로 두는 방법이 있었다.
  그러면 표 머리와 같은 색이 되어 한 화면에서 역할이 겹친다.
- 보수적 선택 여부: 예. 덱이 쓰던 색 배치를 그대로 복원했다.
- 계획과의 이탈: 없음. 설계 문서 결정 4번이 옮기라고 한 것을 제대로 옮긴 것이다.
