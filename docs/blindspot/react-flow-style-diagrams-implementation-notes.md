## 2026-07-28 — 작업 브랜치를 따로 판다

- 결정: `react-flow-diagrams` 브랜치를 만들어 거기서 작업한다.
- 이유: 지금 `main`에 있다. 세 자료와 공용 파일 여섯 개를 동시에 건드리는 작업이라 중간 상태가 배포되면 안 된다.
- 검토한 대안: `main`에서 바로 작업하고 한 번에 커밋하는 방법. 이 저장소는 `main`이 곧 배포본이라 위험하다.
- 보수적 선택 여부: 예
- 계획과의 이탈: 없음
- 사용자 확인 필요: 아니오

## 2026-07-28 — 조작 단추를 껍데기 안에 겹쳐 띄운다

- 결정: `.flow-controls`를 `.flow` 껍데기 **안에** 두고 `position: absolute`로 겹쳐 띄운다.
- 이유: 설계 문서는 단추를 껍데기의 형제로 두라고 했다. 이유는 단추 높이가 도식 높이 한도를 잡아먹는 것을 막기 위해서였다.
  겹쳐 띄우면 안에 있어도 높이를 차지하지 않으므로 그 목적이 그대로 달성된다.
  바깥에 두려면 둘을 감싸는 상자를 하나 더 만들어야 하는데, 그 상자는 설계 문서의 여섯 부분 어디에도 없다.
  껍데기가 `role="group"`이라 안에 있어도 단추가 보조 기술에서 사라지지 않는다.
  `data-prevent-swipe`가 껍데기에 붙어 있어 단추 위 터치도 슬라이드를 넘기지 않는다.
- 검토한 대안: 감싸는 상자를 하나 더 만들어 설계 문서 그대로 형제로 두는 방법. 요소가 하나 늘고 얻는 것이 없다.
- 보수적 선택 여부: 예. 설계 문서가 막으려던 결함(높이 잠식)은 그대로 막았다.
- 계획과의 이탈: 있음. 설계 문서 "도식이 어떻게 짜여 있나"의 층 구조에서 단추의 부모가 달라졌다.
- 사용자 확인 필요: 아니오

## 2026-07-28 — 두 손가락 확대를 직접 구현했다

- 결정: 포인터를 목록으로 들고 있다가 둘이 되면 두 손가락 확대로 넘어간다. 두 점 사이 거리의 비율을 배율에 곱한다.
- 이유: 설계 결정 12번이 두 손가락 확대를 넣기로 했다.
  브라우저 기본 동작을 막는 표시(`touch-action: none`)만 걸고 구현을 안 하면 만지는 화면에서 확대가 아예 안 된다.
  그 표시 없이 두면 브라우저 화면 확대가 도식이 아니라 페이지 전체를 키운다.
- 검토한 대안: 손가락 확대를 빼고 단추만 두는 방법. 결정 12번을 조용히 되돌리는 것이라 택하지 않았다.
- 보수적 선택 여부: 아니오
- 계획과의 이탈: 없음
- 사용자 확인 필요: 아니오

## 2026-07-28 — touch-action을 조작이 켜진 동안에만 건다

- 결정: `touch-action: none`을 `.flow.is-live`에만 건다. `is-live`는 조작 가능 상태에서만 붙는다.
- 이유: 항상 걸면 좁은 화면에서 도식 위 손가락 세로 스크롤이 막혀 그 장을 읽을 수 없다.
  좁은 화면·전체 보기·발표자 화면·인쇄 네 상황에서 조작을 끄는데, 그때는 이 표시도 함께 빠져야 한다.
- 검토한 대안: 항상 거는 방법. 좁은 화면에서 덱을 읽을 수 없게 된다.
- 보수적 선택 여부: 예
- 계획과의 이탈: 없음
- 사용자 확인 필요: 아니오

## 2026-07-28 — 껍데기의 box-sizing을 content-box로 되돌렸다

- 결정: `.flow`에 `box-sizing: content-box`를 명시한다.
- 이유: 처음에 `border-box`로 두었더니 인라인으로 준 높이 212픽셀에서 테두리 2픽셀을 빼앗아 안쪽 칸이 210픽셀이 됐다.
  도식은 212픽셀이라 안쪽 칸보다 2픽셀 높아졌고, 그 결과 기본 배율에서도 세로로 밀 수 있게 됐다.
  실측으로 확인했다. 브라우저에서 `is-pannable` 표시가 기본 상태에 붙어 있었다.
  이것은 설계 결정 10번("기본 배율에서는 갈 곳이 없다")과 접근성 논거를 동시에 무너뜨린다.
- 검토한 대안: 인라인 높이를 도식 높이 + 2로 적는 방법. 자료마다 손으로 더해야 해서 틀리기 쉽다.
- 보수적 선택 여부: 예
- 계획과의 이탈: 없음
- 사용자 확인 필요: 아니오

## 2026-07-28 — 도식 상태를 배열이 아니라 요소 자신에 붙였다

- 결정: 상태 객체를 `.flow` 요소의 속성으로 붙이고, 필요할 때마다 화면에서 다시 찾는다.
- 이유: 발표 폭 435픽셀 이하가 되면 발표 도구가 슬라이드 영역을 통째로 다시 만든다.
  처음 구현은 초기화 때 요소를 배열에 담아 두었는데, 다시 만들어진 뒤에는 그 참조가 죽은 요소를 가리킨다.
  창을 좁혔다 넓히면 도식이 조용히 먹통이 됐다. 실측으로 재현했다.
  설계 문서는 "리스너를 바깥에 붙인다"까지만 정했는데, 그것만으로는 부족했다.
  리스너는 살아남지만 상태를 찾는 쪽이 옛 요소를 보고 있었다.
- 검토한 대안: 화면 크기 변화 신호를 받을 때마다 배열을 다시 만드는 방법.
  같은 일을 두 곳에서 관리하게 되어 어긋날 여지가 남는다.
- 보수적 선택 여부: 아니오. 더 단순한 구조로 바꾼 것이다.
- 계획과의 이탈: 없음. 설계 문서가 막으려던 결함을 실제로 막는 데 필요한 보강이다.
- 사용자 확인 필요: 아니오

## 2026-07-28 — 조작이 꺼진 상태에서 단추를 감추는 규칙을 CSS로 넣었다

- 결정: `.flow:not(.is-live) .flow-controls { display: none; }` 한 줄을 넣는다.
- 이유: 설계 결정 19~22번이 네 상황에서 단추를 감추기로 했다.
  구현 후 실측했더니 인쇄에서만 감춰지고 전체 보기·좁은 화면·발표자 화면에서는 그대로 보였다.
  눌러도 아무 일이 없는 단추가 남아 있었다.
- 검토한 대안: 상황마다 따로 규칙을 적는 방법. 네 곳이 되고 하나를 빠뜨리기 쉽다.
- 보수적 선택 여부: 아니오
- 계획과의 이탈: 없음
- 사용자 확인 필요: 아니오

## 2026-07-28 — 연결선 이름표에 배경을 깔았다

- 결정: `.flow-label`에 슬라이드 배경색을 깔고 좌우 여백 6픽셀을 준다.
- 이유: 이름표를 연결선 위에 얹으니 선이 글자를 가로질러 읽기 어려웠다. 스크린샷으로 확인했다.
  설계 문서는 "선 위쪽에 6픽셀 띄운다"고 했으나, 실제로 띄우면 상자 글자와 같은 높이가 되어 더 혼란스러웠다.
  전에 쓰던 mermaid 도 이름표 배경을 같은 색으로 깔고 있었다.
- 검토한 대안: 이름표를 선보다 위로 올리는 방법. 상자 글자와 높이가 겹쳐 더 나빴다.
- 보수적 선택 여부: 아니오
- 계획과의 이탈: 있음. 설계 문서의 "선 위쪽에 6픽셀 띄운다"를 "선 위에 얹고 배경으로 가린다"로 바꿨다.
- 사용자 확인 필요: 아니오

## 2026-07-28 — 견본 자료 흐름도의 가로 간격을 60픽셀로 넓혔다

- 결정: 이 도식만 상자 사이 가로 간격을 40픽셀이 아니라 60픽셀로 한다.
- 이유: 이름표 "통과"가 20픽셀 글자 두 자라 40픽셀이다. 배경 여백까지 더하면 52픽셀이라 40픽셀 간격에 안 들어간다.
  60픽셀로 넓히면 상자 다섯 개와 간격 네 개가 1240픽셀이라 슬라이드 1280픽셀 안에 그대로 들어간다.
- 검토한 대안: 이름표 글자를 줄이는 방법. 도식 안에서 가장 작은 글자가 더 작아져 뒷자리에서 안 읽힌다.
- 보수적 선택 여부: 아니오
- 계획과의 이탈: 있음. 설계 문서의 가로 간격 40픽셀과 가로 합계 1160픽셀이 60픽셀과 1240픽셀로 바뀌었다.
- 사용자 확인 필요: 아니오

## 2026-07-28 — 도식에 등장 효과를 걸지 않았다

- 결정: 세 도식 어디에도 등장 효과(`rise`)를 걸지 않는다. 도식은 슬라이드와 함께 바로 나타난다.
- 이유: 설계 결정 29번은 "걸더라도 바깥 껍데기 한 겹에만"이라고 정했지 반드시 걸라고 하지는 않았다.
  안 걸면 등장 순서 값과 자동 검사 2번·4번의 상호작용을 아예 만들지 않는다.
  파일 구조 도식이 들어가는 장은 등장 지연이 1.2초로 설정된 장이라, 도식이 1.2초 뒤에 나타나면 발표 흐름이 끊긴다.
  그 장의 결론 문장은 지금도 1.2초 뒤에 나타나므로 "도식 먼저, 결론 나중"이라는 순서가 오히려 자연스럽다.
- 검토한 대안: 껍데기에 등장 효과를 거는 방법. 얻는 것이 적고 검사와 얽힐 여지만 는다.
- 보수적 선택 여부: 예
- 계획과의 이탈: 없음
- 사용자 확인 필요: 아니오
