# primer-inventory 발표자료 스크립트 작성 및 디자인 개편 요구사항

- 날짜: 2026-07-27
- 상태: 잠정 확정 (미해결 질문은 다음 단계에서 해소)
- 관련 문서: unknowns 미작성 (바로 다음 단계에서 작성), explainer 미작성 (unknowns 해소 후 작성)
- 선행 작업: [발표자료 제작 보고서](2026-07-27-primer-inventory-deck-report.md)

## 용어 안내

여기서 푸는 말은 **이 문서를 읽는 사람**을 위한 것입니다.
발표를 들을 매니저를 위한 것이 아닙니다.

- **덱**: 발표자료 한 벌을 뜻합니다.
  이 저장소에서는 파일 하나가 덱 하나입니다.
- **발표자 화면**: 발표 중에 발표자만 보는 별도 창입니다.
  `S` 키를 누르면 열립니다.
  현재 슬라이드와 다음 슬라이드와 노트와 시계가 함께 나옵니다.
- **발표자 노트**: 슬라이드마다 붙여 두는 메모입니다.
  청중 화면에는 안 보이고 발표자 화면에만 나옵니다.
- **화면 크기**: 슬라이드 한 장의 가로세로 픽셀 수입니다.
  지금은 가로 960에 세로 700입니다.
- **칸**: 글자 너비가 모두 같은 글꼴에서 글자 한 자리를 뜻합니다.
  한글 한 글자는 두 칸을 차지합니다.
- **등장 애니메이션**: 슬라이드 안의 내용이 나타나는 움직임입니다.
- **키를 눌러 하나씩**: 방향키를 누를 때마다 항목이 하나씩 나타나는 방식입니다.
- **자동 등장**: 슬라이드가 뜨면 내용이 저절로 순서대로 나타나는 방식입니다.
- **글자 선명도(대비)**: 글자색과 배경색이 얼마나 다른지를 나타내는 값입니다.
  값이 낮으면 글자가 배경에 묻혀 안 보입니다.
- **자동 검사(CI)**: 코드를 올릴 때마다 저장소가 스스로 돌리는 확인 절차입니다.
- **여러 곳이 함께 쓰는 파일**: 첫 화면과 견본 덱과 이 덱이 같이 불러 쓰는 파일입니다.
  하나를 고치면 셋이 모두 바뀝니다.
- **견본 덱**: 이 저장소에 먼저 있던 시연용 발표자료입니다.
- **첫 화면**: 저장소 주소로 들어가면 나오는 발표자료 목록 페이지입니다.
- **자간 보정 코드**: 한글 글자 폭이 영문의 두 배가 아닐 때 글자 사이를 벌려 표를 맞추는 코드입니다.
  지난 작업에서 덱 안에 넣었습니다.
- **저장 시점(커밋)**: 코드가 저장된 특정 시점을 가리키는 이름표입니다.

## 요청 배경

사용자는 어제 `primer-inventory` 덱을 만들었습니다.
매니저에게 프로젝트를 설명하고 피드백을 받을 자리에 쓸 자료입니다.
슬라이드는 모두 28장입니다.

이제 세 가지를 더 하려 합니다.

1. 발표할 때 볼 **스크립트**를 만듭니다.
2. 그 스크립트를 **발표자 화면**에서 볼 수 있게 합니다.
3. 전체 **디자인과 움직임**을 다른 사이트를 참고해 새로 만듭니다.

참고할 사이트는 `euiyun.com` 입니다.

## 현재 상태 사실 확인

### 발표자 노트

지금도 28장 전부에 노트가 붙어 있습니다.
다만 스크립트가 아니라 짧은 메모입니다.

| 항목 | 값 |
|---|---|
| 노트 개수 | 28개 (모든 슬라이드) |
| 평균 길이 | 93자 |
| 가장 짧은 것 | 23자 |
| 가장 긴 것 | 165자 |
| 전체 합계 | 2,603자 |
| 소리 내어 읽으면 | 약 9분 |

노트 원문은 대부분 여러 줄로 적혀 있습니다.
그런데 줄바꿈 표시를 쓰지 않아서 발표자 화면에서는 한 덩어리로 붙어 나옵니다.

노트의 성격은 세 갈래입니다.
첫째는 화면에 없는 배경을 적은 것입니다.
둘째는 "이 질문이 나오면 부록을 보여 준다"는 조건부 안내입니다.
셋째는 부록이 어디 있는지 적은 운영 메모입니다.

### 발표자 화면의 크기 제약

발표자 화면은 가로 1100, 세로 700 크기의 새 창으로 열립니다.
그 안에서 노트가 차지하는 자리는 가로 440, 세로 420입니다.
그중 위쪽 약 110을 시계와 타이머가 씁니다.
그래서 노트가 실제로 보이는 높이는 약 300입니다.

노트가 넘치면 잘리지는 않고 스크롤이 생깁니다.
다만 발표 도중에 마우스로 스크롤하는 것은 사고나기 쉽습니다.

노트 안에 쓴 서식은 살아 있습니다.
줄바꿈 표시나 굵은 글씨 표시가 그대로 나옵니다.
다만 그냥 줄을 바꿔 쓴 것은 무시됩니다.

### 디자인의 위험 지점

지금 덱에는 글자 크기를 직접 지정한 곳이 65군데 있습니다.
그 65곳은 성격이 둘로 나뉩니다.

**계산으로 정한 8곳**입니다.
터미널 화면과 코드를 담은 상자들입니다.

이 8곳은 두 가지 상한을 동시에 만족해야 합니다.
하나는 가로 폭입니다.
슬라이드 가로 960에서 여백을 뺀 921.6이 기준입니다.
다른 하나는 상자 높이입니다.
공용 스타일 파일이 480픽셀로 막고, 안쪽 여백을 빼면 448픽셀이 남습니다.

**둘 중 더 작은 값이 실제 상한이 됩니다.**
상자마다 어느 쪽이 막는지가 다릅니다.

| 상자 | 줄 | 최대 칸 | 폭이 허용 | 높이가 허용 | 막는 것 |
|---|---|---|---|---|---|
| 부록 코드 | 17줄 | 88칸 | **17.5픽셀** | 22.0픽셀 | 폭 |
| 추천 이유 안내 | 6줄 | 86칸 | **17.9픽셀** | 62.2픽셀 | 폭 |
| 덮임 그림 | 13줄 | 102칸 | **15.1픽셀** | 28.7픽셀 | 폭 |
| 추천 목록 | 12줄 | 101칸 | **15.2픽셀** | 31.1픽셀 | 폭 |
| 제외와 설계 | 16줄 | 97칸 | **15.8픽셀** | 23.3픽셀 | 폭 |
| 명령 한 줄 | 1줄 | 78칸 | **19.7픽셀** | 373픽셀 | 폭 |
| 결합 판정 코드 | 19줄 | 76칸 | 20.2픽셀 | **19.7픽셀** | 높이 |
| 탈락 개수 코드 | 25줄 | 79칸 | 19.4픽셀 | **14.9픽셀** | 높이 |

폭이 가장 빡빡한 것은 **부록 코드**입니다.
여유가 약 1.4칸뿐입니다.

높이가 가장 빡빡한 것은 **탈락 개수 코드**입니다.
25줄이라 14.9픽셀까지만 키울 수 있습니다.

이 두 코드 상자는 실제로는 표의 값보다도 더 작게 쓰고 있습니다.
슬라이드 전체가 세로 700을 넘지 않아야 했기 때문입니다.

**나머지 57곳**은 이 계산과 무관합니다.
본문 목록과 캡션과 표의 글자 크기입니다.
그중 일부는 슬라이드가 세로 700을 넘어서 줄인 값입니다.

넘쳤을 때의 결과는 자리마다 다릅니다.
슬라이드 세로 700을 넘기면 화면 아래가 **잘립니다.**
코드 상자 안에서 넘치면 화면에서는 스크롤이 생깁니다.
다만 그 상태로 인쇄하면 넘친 부분이 잘립니다.

이미 4장이 세로 700을 넘어 글자를 줄인 이력이 있습니다.

### 자동 검사가 잠가 둔 것

별 배경의 수치 세 개를 자동 검사가 정확히 잠가 두었습니다.
별 개수 200개, 최대 밝기 0.5, 최대 이동 폭 30입니다.
이 값을 바꾸면 자동 검사가 반드시 실패합니다.

이 별 배경은 첫 화면과 견본 덱도 함께 씁니다.

## 참고 사이트 사실 확인

`euiyun.com`에는 **성격이 다른 디자인이 두 개** 있습니다.

주소를 그냥 치면 나오는 메인 페이지는 밝은 테마입니다.
주소 뒤에 `/seminar/vibe-coding/`이 붙는 발표자료들은 어두운 테마입니다.
그 발표자료도 지금 덱과 같은 도구로 만들어졌습니다.

확인된 값은 다음과 같습니다.

| 항목 | 값 |
|---|---|
| 배경색 3단계 | `#06080F` / `#0E1220` / `#161B30` |
| 글자색 3단계 | `#FFFFFF` / `#E2E6F0` / `#B8BFD0` |
| 강조색 | 보라 `#9B82FF`, 민트 `#2BEAD0` |
| 보조 강조색 | 분홍 `#FF7A95`, 호박 `#FFD46B` |
| 본문 글꼴 | Pretendard |
| 코드 글꼴 | JetBrains Mono |
| 제목 크기 | 본문의 약 2.9배, 굵기 800 |
| 화면 크기 | 가로 1280, 세로 800 |
| 등장 움직임 | 0.6초, 항목마다 0.15초씩 차이를 둠 |

본문 글꼴과 코드 글꼴은 **지금 덱의 1순위와 같습니다.**
그래서 글꼴 자체는 거의 바뀌지 않습니다.

### 참고 덱의 제작 규칙 중 무엇을 받아들이는가

그쪽 제작자는 슬라이드 제작 규칙을 글로 적어 두었습니다.
아래는 2026-07-27에 확인한 것만 적은 것입니다.
규칙 전부를 읽었다는 뜻은 아닙니다.
확인한 곳은 `github.com/geniuskey/vibe-coding` 저장소의 `making-slides` 자료입니다.

그중 일부만 받아들입니다.

| 규칙 | 이번 작업에서 |
|---|---|
| 색은 정한 팔레트 안에서만 쓴다 | **받아들임** |
| 움직임은 한 가지 패턴을 반복한다 | **받아들임** |
| 움직임을 줄여 달라는 설정을 존중한다 | **받아들임** (지금 덱도 이미 그렇게 함) |
| 슬라이드에 밝은 테마 금지 | **안 받아들임** — 아래 확정 요구사항 9번 참조 |
| 본문 여섯 줄 이하 | **안 받아들임** — 슬라이드 내용 재구성은 이번 범위 밖 |
| 글꼴 파일을 자료 안에 넣는다 | **안 받아들임** — 선행 작업에서 안 넣기로 정했음 |

## 확정 요구사항

1. **참고 대상은 세미나 발표자료 쪽이다.**
   사용자 답변: "세미나 발표자료 쪽."
   메인 페이지의 밝은 테마는 참고하지 않습니다.
   어두운 골격을 그대로 두고 색과 움직임을 가져옵니다.

2. **스크립트는 요점 나열과 꼭 짚을 문장을 섞어 쓴다.**
   사용자 답변: "요점 + 꼭 짚을 문장만."
   말할 순서를 짧게 나열합니다.
   틀리면 안 되는 숫자와 문장만 완성된 문장으로 적습니다.
   그대로 읽는 완전 대본은 만들지 않습니다.

3. **슬라이드당 스크립트는 발표자 화면에 스크롤 없이 들어가야 한다.**
   사용자 답변: "기본 화면에 스크롤 없이."
   발표 중에 마우스로 스크롤할 일이 없어야 합니다.
   글자 수 상한은 200자에서 240자 사이로 추정됩니다.
   정확한 값은 실제로 창을 열어 재야 정해집니다.
   그때까지는 200자를 잠정 상한으로 씁니다.

   총 분량 목표는 두지 않습니다.
   각 슬라이드에 필요한 만큼만 쓰고, 상한만 지킵니다.

4. **화면 크기를 가로 1280, 세로 800으로 바꾼다.**
   사용자 답변: "화면 비율까지 전부."
   참고 덱과 같은 크기입니다.
   가로세로 비율이 약 1.37 대 1에서 1.6 대 1로 바뀝니다.
   글자에 쓸 수 있는 가로 폭이 921.6에서 1241.6으로 늘어납니다.
   약 35퍼센트 넓어집니다.

5. **글자 크기를 다시 계산한다.**
   4번의 결과입니다.

   계산으로 정한 8곳은 **폭과 높이를 각각 계산해 더 작은 값을 씁니다.**
   폭 기준은 새 값 1241.6입니다.
   높이 기준은 코드 상자의 높이 상한입니다.

   폭이 막던 6곳은 크게 키울 수 있습니다.
   예를 들어 부록 코드는 지금 17.1픽셀인데 23.5픽셀까지 갑니다.

   높이가 막던 2곳은 폭이 넓어져도 그대로입니다.
   그 둘은 상자 높이 상한을 풀어야 커집니다.
   상한을 얼마로 풀지는 미해결 질문 7번에서 정합니다.

   나머지 57곳은 새 세로 800을 기준으로 다시 정합니다.

6. **터미널 화면과 코드의 원문은 한 글자도 바꾸지 않는다.**
   선행 요구사항에서 이어받은 항목입니다.
   글자 크기만 바꾸고 내용은 그대로 둡니다.
   작업 후 원본 파일과 기계로 다시 대조합니다.

7. **슬라이드 안의 내용이 자동으로 순서대로 나타나게 한다.**
   사용자 답변: "참고 덱처럼 자동으로 다 나오게."
   지금은 방향키를 눌러야 하나씩 나옵니다.
   슬라이드 안에서 하나씩 나오는 항목이 28개 있습니다.
   앞으로는 슬라이드가 뜨면 저절로 나타납니다.
   나타나는 모양은 아래에서 위로 올라오며 서서히 진해지는 방식입니다.

8. **코드의 줄 강조만 키 입력을 유지한다.**
   자체 해소한 항목입니다.
   코드 슬라이드 두 장은 방향키를 누를 때마다 다른 줄이 밝아집니다.
   이건 발표자가 설명 속도를 잡아야 하는 자리입니다.
   자동으로 넘어가면 설명할 시간이 없습니다.

9. **밝은 화면 모드를 그대로 유지한다.**
   사용자 답변: "그대로 유지."
   참고 덱의 규칙과 어긋나지만 사용자 지시를 따릅니다.
   조명이 밝은 강의실에서 쓸 수 있어야 하기 때문입니다.
   새 색을 밝은 버전으로도 만듭니다.
   작업 후 28장 전부의 글자 선명도를 다시 잽니다.

10. **여러 곳이 함께 쓰는 파일과 견본 덱은 건드리지 않는다.**
    자체 해소한 항목입니다.
    근거는 선행 작업에서 같은 원칙을 세웠고 그 이유가 기록되어 있다는 점입니다.
    대상은 스타일 파일 두 개와 별 배경 파일과 그 검사 파일입니다.
    `assets/galaxy.css`, `assets/galaxy-reveal.css`, `assets/starfield.js`, `assets/starfield.selftest.js` 입니다.
    이 파일들을 고치면 첫 화면과 견본 덱까지 바뀝니다.
    새 스타일은 이 덱 파일 안에만 넣습니다.

    코드 상자의 높이 상한 480픽셀도 공용 파일에 있습니다.

11. **노트에는 줄바꿈 표시를 직접 넣는다.**
    자체 해소한 항목입니다.

    그래서 줄바꿈 표시나 목록 표시를 직접 써야 합니다.

12. **대상 저장소의 참조 시점은 그대로 둔다.**

## 미해결 질문

아래 항목은 다음 단계에서 다룹니다.

1. 발표자 화면 노트 상자에 스크롤 없이 들어가는 글자 수가 정확히 얼마인가.
   노트 글자 크기가 19.2픽셀이 될 수도 있고 21.6픽셀이 될 수도 있습니다.
   창 폭에 따라 갈립니다.
   실제로 창을 열어 재야 확정됩니다.

2. 화면 크기를 바꾼 뒤 상자 8개의 새 글자 크기가 얼마인가.
   폭과 세로를 각각 다시 계산해야 합니다.
   자간 보정 코드도 새 글자 크기로 다시 재야 합니다.

3. 배경 연출을 어떻게 할 것인가.
   참고 덱은 배경이 네 겹으로 겹쳐 있습니다.
   그라디언트와 입자와 격자와 어둡게 덮는 층입니다.
   지금 덱은 별이 움직이는 배경 하나입니다.

   선택지가 셋입니다.
   첫째, 별 배경을 그대로 두고 덱 안에서만 위에 한 겹을 더 얹습니다.
   이 방법은 확정 요구사항 10번을 지킵니다.
   둘째, 별 배경의 수치를 바꿉니다.
   이 방법은 자동 검사가 실패하므로 검사 파일도 함께 고쳐야 합니다.
   첫 화면과 견본 덱의 배경도 함께 바뀝니다.
   즉 확정 요구사항 10번을 깨는 선택입니다.
   셋째, 이 덱에서만 별 배경을 끄고 다른 배경으로 바꿉니다.

4. 새 강조색이 밝은 화면 모드에서 선명도 기준을 넘는가.
   보라와 민트는 어두운 배경에 맞춰 고른 색입니다.
   밝은 배경에서는 다른 값이 필요할 수 있습니다.

5. 자동 등장으로 바꾸면 슬라이드 번호 표시가 달라지는가.
   지금은 오른쪽 아래에 몇 번째 장인지 나옵니다.
   키로 하나씩 나오던 것을 없애면 그 셈이 달라질 수 있습니다.

6. 스크립트 내용을 어디에서 끌어올 것인가.
   지금 노트 2,603자가 출발점입니다.
   나머지는 선행 작업의 문서들에서 가져올 수 있습니다.
   어느 문서의 어느 부분을 쓸지 정해야 합니다.

7. 코드 상자의 높이 상한 480픽셀을 덱 안에서 어떻게 풀 것인가.
   공용 파일을 못 고치므로 덱 안에서 덮어써야 합니다.
   얼마로 풀지는 새 글자 크기가 정해진 뒤에 계산됩니다.
